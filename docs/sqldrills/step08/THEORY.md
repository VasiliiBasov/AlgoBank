## 0. Главная мысль: JOIN = декартово произведение + фильтр

Логическая модель (не физика выполнения — см. §8). Когда пишешь

```sql
SELECT a.owner_name, t.amount_minor
FROM account a
JOIN transactions t ON t.account_id = a.id;
```

база **логически** делает так:

```
1. FROM a JOIN t — сначала мысленно строится КАЖДАЯ строка a × КАЖДАЯ строка t
   (4 счёта × 10 транзакций = 40 пар-кандидатов)
2. ON            — из этих 40 пар выживают те, где условие TRUE
   (t.account_id = a.id → 10 пар; пара «Иван × чужая транзакция» отлетает)
3. WHERE         — (если есть) фильтрует уже построенные пары
4. SELECT        — вычисляет выходные колонки выживших пар
```

Следствия, за которые цепляют:

- **Число строк может взорваться.** Если у счёта 3 транзакции — он появится
  в результате 3 раза. «JOIN удвоил мне строки» = у правой таблицы было по 2
  совпадения на ключ. Это не баг — это произведение.
- **`ON` — это просто предикат над парами.** Можно `ON t.amount_minor > 0`
  (неэквивалентное условие!) — пары будут искаться по сумме, а не по связи.
  Неэквивалентные ON — главный инструмент q06.
- **`CROSS JOIN`** — произведение без фильтра вообще (`FROM a CROSS JOIN t` =
  `FROM a, t` = все 40 пар). Знать название обязательно: «как получить декартово
  произведение?» — классика собеса.

## 1. Четыре вида: что делать с НЕсматчей

Разница между видами JOIN — только в судьбе строк, у которых **не нашлось пары**:

| Вид | Несматч слева (счёт без транзакций) | Несматч справа (транзакция без счёта) |
|---|---|---|
| `INNER JOIN` (= `JOIN`) | выбрасывается | выбрасывается |
| `LEFT [OUTER] JOIN` | **остаётся**, колонки правой = NULL | выбрасывается |
| `RIGHT [OUTER] JOIN` | выбрасывается | **остаётся**, колонки левой = NULL |
| `FULL [OUTER] JOIN` | **остаётся** | **остаётся** |

- `INNER` — пересечение по совпадениям: только пары «есть с обеих сторон».
- `OUTER`-виды добавляют обратно строки-«не сматчились» с NULL-ами на пустой
  стороне. Слово `OUTER` необязательно (`LEFT JOIN` = `LEFT OUTER JOIN`), но
  на собесе произноси полное название, чтобы услышали знание.
- Венна-диаграммы (кружочки) — хорошая мнемоника для старта, но **врут про
  мультипликацию**: множества не показывают, что одна строка слева может
  породить несколько строк результата. Держи в голове §0, не кружочки.

На наших данных: счёт 4 (Анна) — без транзакций; «сиротских» транзакций
(без счёта) в сиде нет → при джойне по `account_id` FULL совпадёт с LEFT.
Помни это при q06: заставить FULL показать специфику — твоя задача через ON.

## 2. ON vs WHERE — ловушка №1 блока

Логический порядок расширяется (по сравнению с теорией блока 7, §0):

```
1. FROM ... JOIN ... ON     — произведение + отбор пар (+ возврат несматчей у OUTER)
2. WHERE                    — фильтрация ПОСТРОЕННОГО результата
3. SELECT … 4. ORDER BY … 5. LIMIT …
```

Отсюда два факта уровня «спрашивают каждого джуна»:

- **У INNER условие в ON и в WHERE эквивалентны** — отфильтровать пары до
  или после произведения, результат один. (Оптимизатору всё равно, он сам
  переносит.)
- **У OUTER — НЕ эквивалентны.** ON решает «что считается парой» (несматчи
  всё равно вернутся с NULL-ами); WHERE режет ** уже построенное** — включая
  строки с NULL. Классический сюрприз:

```sql
-- Хотел «все счета + их положительные транзакции», написал:
FROM account a LEFT JOIN transactions t ON t.account_id = a.id
WHERE t.amount_minor > 0
-- …и получил INNER! Строка Анны (NULL в amount_minor) не проходит
-- «NULL > 0 → UNKNOWN → строка вылетает». Фильтр положительных
-- надо было класть в ON, не в WHERE (смысл q06 — именно это).
```

Правило: **условие «какие пары считать» — в ON; условие «какие итоговые строки
отдать» — в WHERE.** Фильтр по правой таблице в WHERE убивает LEFT-смысл.

## 3. NULL при JOIN — ловушка №2

- **`NULL` не равен ничему, даже `NULL`** (трёхзначная логика из блока 7):
  `t.account_id = a.id` никогда не сматчит две NULL-ки друг с другом.
  Строка с NULL в ключе соединения — в INNER пропадает молча, в OUTER —
  остаётся несматчем. Поэтому FK с NULL — ловушка данных.
- **`anti-join`** — самый частый «JOIN на собесе»: «дай счета БЕЗ транзакций».

```sql
FROM account a LEFT JOIN transactions t ON t.account_id = a.id
WHERE t.id IS NULL          -- выжили только несматчи: пара не нашлась
```

Это читается быстрее и безопаснее, чем `NOT IN (SELECT …)` (который при NULL
в подзапросе вообще пуст — трёхзначная логика кусается; подзапросы — блок 10,
но ловушку запомни уже: `NOT IN` + NULL = пустой результат).

- NULL-ячейки в выводе — это NULL, не 0 и не ''. Для подмены — `COALESCE(x, '…')`.
- **Сортировка с NULL**: в H2 при `ASC` NULL уезжает в конец («больше всех»),
  при `DESC` — в начало. Не полагайся на умолчание: `ORDER BY col NULLS LAST`
  читается без диалектных сюрпризов.

## 4. LEFT ↔ RIGHT: зеркальная эквивалентность

```sql
FROM account a LEFT JOIN transactions t ON ...   ≡
FROM transactions t RIGHT JOIN account a ON ...   -- тот же результат
```

Правую руку можно всегда переписать левой: переверни FROM и поменяй вид.
Поэтому в коде RIGHT встречают редко (читают слева направо, LEFT естественнее),
но **на собесе спросят именно эквивалентность** — «перепиши RIGHT через LEFT».
Цель q05 — прочувствовать это руками: тот же результат из зеркального запроса.

## 5. FULL OUTER JOIN: когда обе стороны «сиротеют»

FULL возвращает: сматчившиеся пары + несматчи слева + несматчи справа
(у несматчей противоположная сторона — NULL). В реальной жизни FULL редок
(реестры-расхождения: «есть в А, нет в Б» и наоборот), на собесе — любимый
«а что будет, если…».

Наш кейс q06: условие соединения `t.account_id = a.id AND t.amount_minor > 0`
(положительность — **в ON**, см. §2!). Что происходит:

- **Пары** образуются только для положительных транзакций.
- **Счета без положительных транзакций** (Анна — без любых) выпадают несматчем
  слева → строка с NULL-ами справа.
- **Отрицательные транзакции** не сматчились ни с одним счётом (условие ON
  для них false!) → выпадают несматчами справа → строки с NULL-ами слева.

Итого NULL-ы с обеих сторон — по 11 строкам на наших данных. Вот почему сORTИРОВКА
там требует `NULLS LAST` дважды (§3): и владелец, и id транзакции бывают NULL.

## 6. Self-join: таблица играет две роли

Таблица может джойниться сама с собой — тогда **обязательны два алиаса**:

```sql
SELECT e.name AS worker, m.name AS boss
FROM employee e
JOIN employee m ON m.id = e.manager_id;   -- классика «начальник подчинённого»
```

- Без алиасов `e`/`m` колонки неразличимы — база не поймёт, чей `name` где.
- Мысленно это две независимые копии таблицы; ON связывает копию-копию.
- При поиске **пар-двойников** (q07) запрос вернёт пару дважды зеркально
  («8 с 10» и «10 с 8»). Приём: `AND t1.id < t2.id` — оставляет из зеркала
  одну половину.

## 7. Мульти-JOIN: цепочки и именование ролей

JOIN'ы складываются цепочкой: каждый следующий ON — предикат к уже
построенному произведению. В q07 будет 4 таблицы в FROM: `t1`, `t2`
(две копии транзакций) + `account` дважды (владелец первой и второй) —
**одна таблица = одна роль**, алиасы говорят, какая именно
(`owner_from`, `owner_to` и т.п. — привычка нейминга, которую ценят на ревью).

Помни §0: каждый JOIN **умножает** строки на среднее число совпадений.
Цепочка из 5 джойнов без усмотрения — типичный способ получить 10⁶ строк
вместо 10². На собесе: «JOIN-ы исполняются слева направо?» — логически да
(цепочка), физически оптимизатор сам выбирает порядок (§8).

## 8. Как база выполняет JOIN физически (ликбез для собеса)

Логическая модель §0 — не то, что реально делает движок. Три алгоритма:

- **Nested Loop** — внешний цикл по левой, внутренний поиск справа (по индексу —
  дёшево; без индекса — полный перебор = катастрофа на больших таблицах).
- **Hash Join** — по меньшей таблице строится хеш-таблица по ключу соединения,
  большая «пробивается» через неё. Дёшево для равенств (`=`), нельзя для `<`.
- **Merge Join** — обе таблицы предсортированы по ключу, слияние двух потоков
  за один проход (как в merge sort).

Вывод для ответа «какой join быстрее?»: правильный ответ — **«зависит от
данных, индексов и селективности; смотрю план (EXPLAIN)»**. Индекс по FK
(`transactions.account_id`) — то, что делает Nested Loop разумным.
EXPLAIN — шаг 19, но фразу «сначала план» можешь говорить уже сейчас.

## 10. Мини-словарь блока

**equi-join** — соединение по равенству ключей (наш обычный случай);
**non-equi-join** — по `<`, `BETWEEN` и т.п. (условие в q06 — смесь).
**anti-join** — «строки левой, у которых нет пары» (LEFT + IS NULL / NOT EXISTS).
**semi-join** — «строки левой, у которых пара ЕСТЬ, но колонки правой не нужны»
(`EXISTS` — блок 10).
**сиротская строка (orphan)** — запись без пары на другой стороне соединения.
**кардинальность связи** — сколько строк справа приходится на строку слева
(1:N у счёта → транзакций); именно из неё растёт «взрыв строк».
