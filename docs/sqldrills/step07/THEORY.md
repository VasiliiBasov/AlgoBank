## 0. Главная мысль: порядок написания ≠ порядку выполнения

Пишем запрос в таком виде:

```sql
SELECT ..., ..., ...
FROM ...
WHERE ...
ORDER BY ... [ASC|DESC]
LIMIT n;
```

А база **выполняет** его (логически) в другом порядке:

```
1. FROM      — какая таблица(ы), откуда берутся строки
2. WHERE     — фильтрация СТРОК (строка либо проходит, либо вылетает)
3. (позже: GROUP BY → HAVING — блок шага 9)
4. SELECT    — вычисляются выражения/колонки; ЗДЕСЬ рождаются алиасы (AS)
5. DISTINCT  — срезание дублей ПОСЛЕ того, как посчитали SELECT
6. ORDER BY  — сортировка результата; поэтому может ссылаться на алиасы
7. LIMIT     — отрезать хвост
```

Следствия, за которые цепляют на собеседовании:

- **«Почему в WHERE нельзя использовать алиас из SELECT?»** — WHERE выполняется
  раньше SELECT: когда фильтруем строки, алиаса ещё не существует.
- **«А в ORDER BY — можно?»** — можно, ORDER BY позже SELECT.
- **«Где выполняется DISTINCT?»** — после SELECT: считается по итоговому набору
  колонок, а не «по таблице».

## 1. SELECT: колонки, выражения, алиасы

```sql
SELECT owner_name, balance_minor / 100 AS balance_rub FROM account;
```

- В списке могут быть: колонки, **выражения** (арифметика, конкатенация, функции),
  литералы. `SELECT *` — все колонки в исходном порядке; на собесе/код-ревью спрашивают
  «зачем `*`» — ответ: только когда просят все колонки (в наших задачах — только Q1).
- `AS` — алиас (имя выходной колонки). Для выражений алиас обязателен по
  здравому смыслу: иначе колонка получит машинное имя вроде `(balance_minor/100)`.
- Регистр ключевых слов не важен (`select` = `SELECT`), но стиль курса — ключевые
  слова КАПСОМ, имена таблиц/колонок — нижним регистром.
- **Алиас колонки vs алиас таблицы.** Колонка: `description AS d` — создаётся в SELECT
  → доступна только в ORDER BY / HAVING / выводе (§0). Таблица: `FROM transactions AS t`
  — создаётся в FROM (шаг 1!) → доступна везде: `t.description` в WHERE/SELECT/ORDER BY.
  Без алиаса: полное квалифицированное имя `transactions.description`. Верное правило:
  **«время жизни имени = этап, где оно создано»**. Алиасы таблиц — must-have в JOIN
  (неоднозначность колонок) и обязательны в self-join (блок 8); в одиночной таблице —
  вкусовщина, обычно при длинных именах. Строковые литералы — в одинарных кавычках
  `'текст'`; двойные `"..."` — идентификаторы (имена колонок/таблиц).

## 2. WHERE: предикаты

Операторы сравнения: `=`, `<>` (или `!=`), `<`, `<=`, `>`, `>=`.
Связки: `AND`, `OR`, `NOT` — приоритет: `NOT` > `AND` > `OR`; сомневаешься — ставь
скобки, это читаемость, а не слабость.

Специальные предикаты:

```sql
WHERE balance_minor BETWEEN 50000 AND 150000   -- ВКЛЮЧИТЕЛЬНО обе границы
WHERE owner_name IN ('Иван Петров', 'Анна Козлова')  -- равносильно цепочке OR по =
WHERE description LIKE 'зарплата%'             -- % = любой хвост любой длины
WHERE description IS NULL                      -- единственно верная проверка на NULL
```

- **BETWEEN a AND b** — это `>= a AND <= b`, границы входят. Ловушка собеса: «будет ли
  строка со значением ровно b?» — будет.
- **IN (…)** — короткая запись `= x OR = y OR = z`.
- **LIKE**: `%` — любая последовательность (в т.ч. пустая), `_` — ровно один символ.
  `'кофе%'` — начинается; `'%кофе'` — заканчивается; `'%кофе%'` — содержит.
- **IS NULL / IS NOT NULL** — единственный способ сравнения с NULL. См. §3, почему.

## 3. NULL и трёхзначная логика (сердце блока)

NULL = «значение неизвестно», это **не** пустая строка и не ноль.
Поэтому логика SQL не двоичная, а **трёхзначная**: TRUE / FALSE / **UNKNOWN**.

| выражение         | результат |
|-------------------|-----------|
| `NULL = NULL`     | UNKNOWN   |
| `NULL <> 5`       | UNKNOWN   |
| `NULL + 1`        | NULL      |
| `5 = NULL`        | UNKNOWN   |

Правило фильтрации: строка проходит WHERE, только если предикат **TRUE**
(FALSE и UNKNOWN — отбрасываются). Отсюда главная ловушка:

```sql
WHERE description = NULL     -- всегда UNKNOWN → вернёт НОЛЬ строк, даже если NULL'ы есть
WHERE description IS NULL    -- правильно
```

Отсюда же — поведение агрегатов (пригодится с блока 9, но спросят уже сейчас,
см. разминку-сессии 25.09):

- `COUNT(*)` — число **строк**;
- `COUNT(колонка)` — число строк, где колонка **не NULL**;
- `COUNT(NULL)` — выражение всегда NULL → всегда **0**;
- `SUM/AVG/MIN/MAX(колонка)` — NULL'ы игнорируются (а не «портят» итог).

Упоминание на будущее (ловушка NOT IN): `x NOT IN (1, 2, NULL)` всегда даёт UNKNOWN
→ ноль строк. Лечится через `NOT EXISTS` (это блок шага 8, там и разберём).

`COALESCE(a, b)` — первый не-NULL аргумент: удобная замена NULL значением по
умолчанию, например `COALESCE(description, 'без описания')`.
## 4. LIKE глубже

- Шаблон сравнивается посимвольно: `'зарплата%'` матчит «зарплата сентябрь», но НЕ
  «предзарплата» (потому что шаблон требует буквы «зарплата» с самого начала).
- Регистр букв зависит от базы и её настроек; в нашей дрели (H2) строковые
  сравнения регистрозависимы — «Зарплата%» и «зарплата%» это разные шаблоны.
  Поэтому в задачах точно копируй первую букву из постановки.
- Спецсимволы шаблона `%` и `_` экранируются: `LIKE '50\%%' ESCAPE '\'` (понадобится
  редко, знать — на одной строке памяти).

## 5. ORDER BY

```sql
ORDER BY balance_minor DESC        -- DESC — по убыванию, ASC — по возрастанию (умолчание)
ORDER BY account_id, amount DESC   -- несколько ключей: сначала по первому, при равенстве — по второму
```

- Можно сортировать по алиасу из SELECT (см. §0) и даже по номеру колонки
  (`ORDER BY 2`) — но по номеру не пишется: нечитаемо.
- **Тип определяет сортировку**: `100000, -4500, -450` как числа идут по величине
  (и помни: -450 > -4500!), а как строки `'1','10','2','3'` — лексикографически.
  Ловушка собеса: «почему 10 стоит раньше 2?» → колонка строковая, а не числовая.
- NULL в сортировке: в H2 при ASC NULL считается «больше всех» и уезжает в конец
  (при DESC — в начало). Явно управляется словами `NULLS FIRST|LAST`.
- Без ORDER BY порядок строк **не определён и не гарантирован** — отсюда правило
  нашего харнесса: осознанный ORDER BY в каждой задаче с несколькими строками.

## 6. DISTINCT

```sql
SELECT DISTINCT amount_minor FROM transactions;  -- набор уникальных значений
```

- Применяется ко **всему списку** колонок: `DISTINCT a, b` срезает дубли пар (a, b),
  а не «a пополам».
- Выполняется после SELECT (§0) → это дополнительная сортировка/хеширование.
  На больших таблицах — не бесплатно.
- Антипаттерн junior'а: писать DISTINCT «на всякий случай». Ревью-вопрос курса:
  «зачем здесь DISTINCT, какой дубль ты убираешь?» — нет ответа → не пиши.
- NULL — одно такое значение в наборе DISTINCT (не «неизвестно игнорируется»).

## 7. Арифметика и целочисленное деление

```sql
SELECT balance_minor / 100 AS balance_rub FROM account;      -- BIGINT / BIGINT = BIGINT (усечение!)
SELECT balance_minor / 100.0 AS balance_rub FROM account;    -- 100.0 → дробное деление
```

- Деление целых чисел отбрасывает дробную часть: `2350.99` из копеек не получишь
  через `minor/100` — получишь `2350`. Хочешь дробь — дели на `100.0` (или CAST).
- Формат курса-данных: суммы в минорных единицах (копейки). На собесе любят спросить,
  почему хранить деньги в BIGINT копеек, а не DOUBLE: DOUBLE — приближённый,
  0.1+0.2≠0.3; копейки — точные. (У нас это Money-копейки из шага 2.)
- В выражениях участвует вся трёхзначность NULL: `5 + NULL → NULL` (§3).

## 8. LIMIT (и предвкушение шага 11)

```sql
SELECT ... FROM ... ORDER BY amount_minor DESC LIMIT 2;   -- топ-2
SELECT ... FROM ... ORDER BY id LIMIT 10 OFFSET 20;        -- страница 3 по 10
```

- LIMIT отрезает хвост после сортировки (§0) — «топ-N» = ORDER BY + LIMIT.
- OFFSET — пропуск первых строк. На наших дрелях OFFSET почти не нужен; в шаге 11
  разберём, почему OFFSET-пагинация душит большие таблицы и чем keyset лучше.
